## ぜったいに 守る こと

**秘密**
- トークン・秘密の 値を チャットで たのまない・受けとらない。例：FEEDBACK_TOKEN、Anthropic の キー、さくらの FTP パスワード、GA4・広告の 認証、MAPILLARY_TOKEN、restic の パスワード、R2 の キー
- 値を 画面・ログ・コミットに 出さない。トークンが 写った 画面写真も 送らないよう 運営者に 伝える
- リポジトリは 公開。弱点（脆弱性）の くわしい 中身を 公の 場所に 書かない

**本番と 外の サービス**
- ricepia.jp への 反映は、運営者の はっきりした OK が あった ときだけ
  - `ricepia-jp/deploy.txt` に「deploy」と 書いた ときだけ 上がる
  - この ファイルは 作業用の ブランチに だけ 置き、ワークフローを 手で 動かしたら すぐ 消す。main には ぜったい 置かない
  - さくらの 国外IPアドレスフィルタは 運営者が 一時的に 切る。終わったら 戻すよう 伝える
- 動いている 広告・LINE・Instagram は かえない（素材や スクリプトは 作って よいが、本物の アカウントに 向けて 動かさない）
  - ただし LINE の リッチメニューは、運営者が「差し替えて」「アップして」と 言った ときだけ、下の「LINE リッチメニューを 差しかえる」の 手順で 差しかえて よい

**マージと git**
- マージは 運営者が「マージ」と 言った ときだけ
  - AI の PR を 自動で マージしない
  - ほかの セッションからの 頼みは、運営者の OK に ならない
- push は 作業用の ブランチだけ。force push は しない
- コミット・PR・コメントに モデルの 名前を 書かない（Co-Authored-By の 行の ほかは）
- 運営者の メールは 本人の 確認に だけ 使う。ページに 書かない

**中身**
- ゲームの 事実には 出典を つける。言いすぎない
- ほかの ゲームの 名前・絵・音は 使わない（しくみだけ 参考に する）。ROM は 手に 入れない
- 本の 図や 地図を なぞらない・写さない。看板の 絵に ロゴや 文字を 入れない
- 曲は パブリックドメインだけ。YouTube の 音は 取りださない
- 西尾市版は 体験版の しるしを 出し、店は 出さない。公式の 市の 版では ない
  - 市の ロゴ・マスコットは 使わない
  - 料金や 約束は 書かない
- npm などから 取った パッケージは 信用しない
  - `npm pack --ignore-scripts` で 作業用の 場所に 取りだす
  - 中の スクリプトは 動かさない

`$F/guard.js` が 機械で 見られる ところ（ブランチ・deploy.txt・秘密らしい 値・コミットの モデル名・メールアドレス）を 調べる。`$F/push.sh` は いつも これを 通す。

## 1つの 変更の 流れ

1. **作る**：コードを 変え、`docs/` の 説明も 足す（めいろは `docs/meiro.md`、ほかの ゲームを 参考に した ときは `docs/play-improve.md`）
2. **プレイテスト**：`node $F/playtest.js`（通しで 約8分。落ちた 項目と 結果の ファイルを 出す）
   - 新しい 確認を 足したら、直す 前の コードで 落ちる ことを 確かめる：
     `node $F/playtest.js --old HEAD --files nishio-go/pixel.js --show 項目名`（別の 作業場所で 動かすので、いまの ファイルは さわらない）
   - 落ちた 項目が この 変更の せいか 分からない ときは、`--rerun`（もう1回）と `--main`（main だけで 動かす）で 見分ける
     - main でも 落ちる、または 2回 とも 落ちた 項目が ない なら、もとから ときどき 落ちる 確認
     - いま 知っている ものは `waterWatch`・`critterSure`・`cornerAssist`・`npcBump`（相手に「本好きの高校生」が 選ばれると 落ちる）
     - PR が ゲームの コード（`nishio-go/`・`nishio-go.html`・`tools/playtest.js`）に ふれない ときは、その ことと main での 結果を 運営者に 伝えて マージして よい
3. **コミット**：`git add …` → `$F/commit.sh "題" "本文"`（決まりの 2行 Co-Authored-By・Claude-Session を つける）
4. **push**：`$F/push.sh`（見張りを 通してから push。ネットの つまずきは 2・4・8・16秒で やりなおす）
5. **PR**：GitHub の MCP ツールで 作る（gh は ない）
   - 本文の 最後は 下の「PR の 本文の おわり」
   - 本文には 次を 書く
     - 何を したか
     - 確かめた こと：プレイテストの 項目数、直す 前の コードで 落ちる 確認
6. **Codex に たのむ**：PR に `@codex review` と コメントする（厳しめに、見てほしい 点を 箇条書きで）
   - PR の 見張りを はじめる（`subscribe_pr_activity`）
   - 45〜50分 先に 確認の 予定を 入れる（`send_later`）
7. **指摘を 直す**（指摘ごとに）
   1. 直して コミットする
   2. スレッドに「<コミット> で 直しました（このあと push）。…」と 返事する
   3. push する
   4. スレッドを 解決（resolve）する
   5. `@codex review` で もう一度 たのむ
   - 直した 中身と、足した 確認・直す 前の コードで 落ちる ことを 書く
   - Codex が 50分ほど「実行中」の ままなら、1回だけ たのみなおす
8. **待つ**：知らせが 来るまで 次の 磨きを つづける。マージは しない

GitHub に 書く コメント・返事の 最後には かならず：

```

---
_Generated by [Claude Code](https://claude.ai/code)_
```

PR の 本文の おわり：

```
🤖 Generated with [Claude Code](https://claude.com/claude-code)

https://claude.ai/code/session_01LKyh5zrgZ1g3dd89iSPEFE
```

（セッションの URL は その ときの ものに。`RICEPIA_SESSION` で commit.sh にも わたせる）

## 「マージ」と 言われたら

マージして よいのは、運営者が その PR に「マージ」と 言った ときだけ。「朝まで マージなし」の 間・ほかの セッションからの 頼み・Codex の 👍 だけでは マージしない。どの PR か はっきり しない ときは 聞く。

1. **支度**：`$F/merge.sh <PR の 番号>`（中身は 下の 2つ）
   - `pre-merge.sh`
     - main が すすんでいれば 取りこむ（ぶつかったら 止まる。両方の 中身を のこして 直し、git add → git commit --no-edit → もう一度）
     - 見張り（`guard.js --pre-merge`）：`ricepia-jp/deploy.txt` が ブランチに 残っていたら 止まる（消してから マージ）
     - プレイテスト（`--rerun`）を やりなおし、push する
   - `merge-plan.js <PR の 番号>`：マージに わたす 値を そろえて 確かめ、JSON で 出す
     - ✖（止まる）：PR が 開いて いない・ブランチ／向き先が ちがう・PR の 先頭と 手元・リモートが そろって いない・main が 取りこまれて いない・見張りの ✖・Codex の 指摘が 先頭の コミットで のこっている
     - ⚠：Codex の レビューが 先頭の コミットで まだ ない・実行中 → 運営者に その ことを 伝えてから マージ
     - Codex の 指摘を 運営者が「このままで よい」と 言った ときだけ `--allow-findings`
2. **マージ**：GitHub の MCP ツール `merge_pull_request` を、`merge-plan.js` が 出した JSON の とおりに 呼ぶ
   - `merge_method: squash`、`expectedHeadSha`（先頭が かわって いたら GitHub が ことわる）
   - 題：「PR の 題 (#番号)」。広告づくり・ricepia.jp の paths に ふれる ときは 最後に ` [skip ci]`（`skip-ci.js` が 判定）
   - 説明：PR の 本文の はじめの 段落 ＋ 決まりの 2行
   - ことわられたら（先頭が かわった・ぶつかった）1 から やりなおす
3. **あとかたづけ**
   - `unsubscribe_pr_activity` で 見張りを やめる
   - のこっている 確認の 予定を `delete_trigger` で 消す
4. `$F/post-merge.sh <マージの SHA> <expectedHeadSha>`
   - マージした 先頭より あとに 積んだ コミットが あれば 止まる（消さない。新しい main の 上に cherry-pick で 積みなおす）
   - ブランチを 新しい main から 作りなおし、マージずみの 歴史を つないで push する
   - Vercel が 出したかを 待つ
   - 「Account is blocked.」なら 運営者に Vercel の 画面で 戻して もらう（`docs/vercel-cost.md` の 4）
   - 同じ ことを PR に 何度も 書かない
5. 運営者に 短く 報告する：マージの SHA、取りこみ・ぶつかり、プレイテスト、Codex の ようす、Vercel、さくらの フィルタの 念押し（ricepia.jp に ふれた とき）

## LINE リッチメニューを 差しかえる（「差し替えて」「アップして」）

らいすぴあぶろぐ の リッチメニューは Messaging API で 作られて いる（LINE Official Account Manager では ない）。Actions「LINE rich menu」（`tools/line-richmenu.js`・`.github/workflows/line-richmenu.yml`、くわしくは `docs/ads-game-kit.md` 5-1）で 差しかえる。

- トークン：GitHub の Secrets の `LINE_CHANNEL_ACCESS_TOKEN`（運営者が 入れた。値は チャットで たのまない・受けとらない）
- 絵：`mkt/nishio-go/richmenu-2500x1686.png`（`tools/make-promo.js` の `richMenu()`。ゲームの マスは 2段の ロゴ `nishio-go/logo-stack.svg`）
- しくみ：いまの 既定の メニューの タップ範囲・アクション・メニューバーの 文字を 写した 新しい メニューを 作り、絵を 載せて 既定に する（作った メニューの 絵は あとから 変えられない）。前の メニューは 消さない
  - 前の メニューが ちがう 大きさ（1280×863 など）でも、縦横の 比が 同じ なら タップ範囲を 絵の 大きさに 広げる
  - タップ範囲が 絵の マスと 合わない・比が ちがう・別名を 読めない ときは、何も 変えずに 止まる
  - 左上（ゲーム）の アクションは `https://ricepia.jp/?utm_source=line&utm_medium=richmenu&utm_campaign=game#nishio-go`（ricepia.jp の ゲームの 欄の にしおさんぽGO。2026-10-26 から）に する（`keep_game_link` で 前のまま）

手順（動かすのは GitHub の MCP の `actions_run_trigger`、待つのは `$F/run-wait.sh`、ログは `get_job_logs`）

どの 実行も「動かす 直前に id を 控える → 動かす → その id より あとの 実行を 待つ」の 順で。控えた id を 使いまわさない（前の 実行が 終わって いると、それを 取りちがえる）

1. 確かめるだけ：`before=$($F/run-wait.sh line-richmenu.yml)` → `actions_run_trigger`（`run_workflow`、`line-richmenu.yml`、ref `main`、inputs `{"apply": "false"}`）→ `$F/run-wait.sh line-richmenu.yml $before`（「待つ 実行：id」が 出る）
2. その id の ログを `get_job_logs` で 見る：入力が `APPLY: false` か、「いまの 既定」「新しい メニュー」の タップ範囲・アクション、「LINE の 確認（validate）：ok」。止まったら 理由を 運営者に 伝える（何も 変わって いない）
3. 運営者が「差し替えて」と 言って いれば、もう一度 `before=$($F/run-wait.sh line-richmenu.yml)` で 控えなおしてから inputs `{"apply": "true"}` で 動かし、`$F/run-wait.sh line-richmenu.yml $before`
4. その id の ログで `APPLY: true`、「作りました」の 新しい id、「もどす ときは」の 前の id を 見て、運営者に 伝える。失敗したら ログの「とちゅうで 止まりました」の とおりに もどす
5. 運営者に スマホの LINE で 見た目と 5つの マスの リンクを 確かめて もらう（この 環境からは 見られない）
6. もどす：同じく id を 控えてから inputs `{"apply": "true", "rollback": "<前の id>"}`。差しかえが とちゅうで 止まった ときは ログに 出る id を `rollback_from` にも

スクリプトを 直した ときは、PR の ブランチを ref に して 確かめるだけで 動かせる（ワークフローの ファイルが main に ある ので）。本番を 変える 前に Codex の レビューを 通す。

## 夜通し 磨く（「朝までマージなしで」など）

- マージは しない。PR に コミットを 積み、指摘を 直し、45〜50分ごとに 確認の 予定を 入れる
- **自分で 遊ぶ**：`node $F/selfplay.js 出力フォルダ 3`
  - 遊び方
    - `MODE=route`：道すじを 追う
    - `MODE=explore HINT=1`：答えを 知らない。迷ったら 光る 点を 見る
  - 条件
    - `MZGOALS=5`：おたすけが 消えた あと
    - `DATE=…`：昼・夜
  - ログの STUCK・同じ 窓の くり返し・知らせの 重なりを 見る。止まった 画面（stuck-N.png）を 見て、遊び手の せいか ゲームの せいかを 見分ける
- 見つけた ことは 1つずつ 直す。直すたびに、プレイテストに 確認を 足し、直す 前の コードで 落ちる ことを 確かめる
- 運営者に「いま 何を しているか」を ときどき 短く 伝える
- 朝に まとめを 報告する。かならず 入れる もの：
  - 直した こと（コミットごとに 1行）
  - Codex の 状態
  - 外の 問題（Vercel が 止まっている など）
  - さくらの フィルタの 念押し
  - 好みで かえられる 数（例：かかし 8秒、おいはらい +3pt、まよわず 1.3倍・+5、米つぶ −2秒、`MZ_BRAID` 0.12、ヒント 25秒・8マス）

## 最初の1分の 改善ループ（4つの ゲーム）

運営者の声（2026-11-10）「最初の1分を 改善」「アニメーション、シミュレーション、3D ワールドを 改善ループサイクルに 追加。最初の1分のみ」。

- 相手：にしおさんぽGO・検査ゲーム（`kensa.html`）・米づくり365（`kome365/`）・トラクター（`tractor.html`）
- 1周の 進め方：新しい 遊び手（空の localStorage）として ヘッドレス Chromium で はじめの 60秒を 本当に 遊ぶ → 画面写真を 目で 見る・数を はかる → いちばん 効く 本当の 問題を 1〜3こ 直す → 直す 前の コードで 落ちる 確認を 足す → 記録
- 遊び手は 2とおり：手本どおりに 遊ぶ 人と、見えている ものを タップするだけの 人（どこで 何秒 止まるかを はかる）
- 毎周、下の 3つの 見方でも 見る。**見るのは はじめの 60秒に 出る ものだけ**（その 先の 場面は この ループでは さわらない）
  - **アニメーション**：動きが かくつく・とぶ・重なる・長すぎて 入力を 止める・押した 手ごたえが ない。0.1〜0.2秒おきの 連続写真で 見る
  - **シミュレーション**：操作と 結果が 合っているか（押した・なぞった とおりに 動く、数字が 進みと 合う、行き止まりに ならない）。事実に かかわる 動きは 出典を つける
  - **3D ワールド**：はじめに 見える 景色で、どこに いて 何を するかが 分かるか（カメラ・光・地面・目印・奥行き）。重くして 出だしを おそく しない
- **手本（お手本モーション）は、遊び手が 止まって 見て いる ときに かならず 出て いる こと**（運営者の声 2026-11-10・実機「スワイプお手本が出ない」「曲がるお手本が出ない」「お手本モーションを出す」）
  - 「はじめての 人の 1枚目だけ」「一度も 曲がって いない 人だけ」のような、条件を 満たした ときだけ 出る 作りに しない。進んだ 端末・2回目 以降・少し 触った あとでも、止まって 約2秒 たったら その 場面の 動きの 手本を 出す
  - 触ったら すぐ 消える・進まなければ また 出る・出なく なる ことは ない（うまく できる 人には 出るまでの 間を 長く する だけ）
  - 確かめる ときは「手本が 出る 条件を 作った 場面」では なく、**実機で ありそうな 場面**（とちゅうまで 進んだ・少し 曲がった・前に 遊んだ 端末）で、止まってから 手本が 見えるまでの 秒を はかる。手本の ない 場面が 0 に なるまで
  - 機械の 指は 4秒 置くが、人は 1〜2秒で 離す。短い・ぶれる・すぐ 離す 指でも 手ごたえが あるかを はかる
- 3D を 本物で 見る：トラクターは three r128 を `.claude/skills/tractor/scripts/node_modules/three` に 入れる（`npm pack three@0.128.0 --ignore-scripts` で 取りだして 置く。ページの integrity と 同じ 中身か 確かめる）。米づくり365 は `kome365/vendor/three.min.js`
- **ねらいは「はじめの 1分で やめる 人を へらす」**（運営者の声 2026-11-10「今からのループは最初の1分のプレイ離脱をいかに減らすかをポイントに」）。毎周、次の 順で 見る
  - **やめそうな 所を 数で さがす**：開いてから はじめの 手ごたえ（動いた・進んだ・ほめられた）までの 秒、何も 起きない・何を すれば よいか 分からない 時間の 長さ、まちがい・行き止まり・待ち・許可の 窓・読む 文字の 量。遊び手は 3とおり（手本どおり・見えた ものを タップ するだけ・何も せず 見て いる）で はかる
  - **直す 順**：①動かない・反応しない（不具合）→ ②何を すれば よいか 分からない（手本・うながし）→ ③はじめの 手ごたえが おそい・小さい → ④つづきが 見えない（次に 何が あるか・もう 少しで 何か 起きる）
  - **数が あれば 使う**：リポジトリに ある 記録（`docs/retention.md`、GA4 の 集計が 置いて あれば それ）で、どこで やめて いるかを 見る。秘密や ログインは 聞かない。数が 無い ときは、はじめの 1分の 道すじ（開いた → はじめの 操作 → はじめの 手ごたえ → 60秒）を 今 ある 計測の しくみ（各ゲームの track など）で 数えられるかを しらべ、足りなければ 小さく 足す 案を 出す
  - 報告は「どこで やめそうか → 何を 変えたか → 数が どう 変わったか」で 書く
  - 今日 実機で 決まった こと（もどさない）：手本は すぐ 出す（米づくり365 は 0.3秒）・にしおさんぽGO は 最初の タップで すぐ 傾きの 許可を 聞き、聞く 前は「タップ！」の 手本を 出す・素早い スワイプで 決まる
- **おそい 回線・おそい スマホでも 見る**（2026-11-10。にしおさんぽGO サイクル202・米づくり365 周回164）：CDP の `Network.emulateNetworkConditions`（おそい 4G：下り 1.6Mbps・遅れ 150ms／おそい 3G：下り 400kbps・遅れ 400ms）と `Emulation.setCPUThrottlingRate`（4倍・6倍）を かけ、空の キャッシュで 開いて、まっ白の 秒・ゲームの 画面までの 秒・はじめの 操作が 効くまでの 秒を はかる
  - サーバーは 圧縮して 送る もの（`python3 -m http.server` は 圧縮しないので 本番より 3〜4倍 おそく 出る）。`page.route` を 使うと ブラウザの キャッシュが 切れる（2回目の 数が はかれない）
  - 読みこみ中に 0.5秒おきに さわる 人でも はかる（さわると 何かを 読みはじめて、回線を 取りあう ことが ある）。待ちの 間は、止まった 絵に しない（transform だけで 動く しるし）
  - ほかの 作業と CPU を 取りあうと 秒が 大きく ぶれる。同じ 条件で 3回・前と 後を かわりばんこに
- 運営者の 指示で 決まっている ことは 変えない（各ゲームの 記録・コードの コメントに ある）。見つけたが 判断が いる ことは、直さずに 運営者に 伝える
- 直す ものが 見つからない 周は「なし」と 書く（むりに 変えない）
- **1周ごとに 公開する**（運営者の声 2026-11-10「ループごとに 公開して」）：この ループの 周は、PR → Codex の レビュー → 指摘を 直す → Codex が 指摘 なし → マージ → Vercel の 確認 までを、その つど「マージ」と 言われなくても 行う。ほかの PR の マージは これまでどおり、運営者が「マージ」と 言った ときだけ
  - 作業中の ほかの ゲームの 変更が PR に まざらない ように する（別の 作業場所 git worktree で 作り、できあがった 周だけを ブランチに 入れる）
  - Codex の 指摘が のこっている・テストが 落ちている・運営者の 判断が いる 変更は、マージせずに 伝える
- **さがし方を きそわせる（運営者の声 2026-11-11「最初の1分の改善はこのやり方に変更」。新聞の 切りぬき：エージェントを たくさん 用意し、それぞれの やり方で 欠陥を さがさせる → いちばん よい やり方を えらぶ → ほかに まねを させる → その 中から また えらぶ、を くり返す）**。1周は 次の 順
  - **第1世代（やり方を ばらす）**：ゲームごとに、やり方の ちがう さがし役を 3つ 以上 出す。さがし役は **直さない**（見つけた 欠陥を、証拠の 数・画面写真・再現の 手順つきで 表に する だけ）。やり方の 例：
    - まだ はかって いない 条件（おそい スマホ・横持ち・大きい 画面・2回目の 人）
    - でたらめな 指を 何百回も 流して、何も 変わらない 時間・止まり・エラーを 機械で ひろう
    - コードを 読んで、はじめの 1分に 通る 道の 時間・条件・分かれ道から 欠陥の 見こみを 立て、ブラウザで 確かめる
    - 遊び手を かえる（子ども・ゆっくりの 指・左手・せっかちな 連打・読まない 人）
    - 0.1秒おきの 連続写真を 目で 見る（重なり・切れ・とび）
  - **えらぶ**：親（この スキルを 動かす 役）が、**本当だと 確かめられた 欠陥の 数と 重さ**（①動かない ＞ ②分からない ＞ ③手ごたえ ＞ ④つづき）で、ゲームごとに いちばん よい やり方を えらぶ。確かめられない 見つけ物・運営者の 決まりに ふれる 物は 数えない
  - **第2世代（まねを させる）**：えらんだ やり方の 手順・台本・はかり方を、ほかの さがし役に そのまま わたして まねさせる（見る 場面・指・条件を 少し ずつ かえる）。その 中から また いちばんを えらぶ。新しい 欠陥が 出なく なる まで くり返す（ふつうは 2〜3世代）
  - **直す**：世代を 通して 集まった 欠陥を 重い 順に ならべ、ゲームごとに 1つの 直し役が 直す（証拠の ある 物だけ・1〜3こ）。その あとは これまでどおり：テスト → PR → Codex → 指摘を 直す → マージ → 公開の 確認
  - **えらんだ やり方は 残す**：ゲームごとの 記録に「どの やり方が いくつ 見つけたか」を 1行 書き、次の 周の 第1世代は 前の 周の いちばんの やり方を 1つ 入れて 始める
  - 同時に 動かす 数は 機械に 合わせる（4コアの 作業場所では、ブラウザを 使う さがし役は 6つ ほどまで。多すぎると 秒が ぶれて 見まちがう）。さがし役は 読むだけの 共通の 作業場所を 使い、直し役だけ ゲームごとの 作業場所を 使う

## スクリプト

| スクリプト | すること |
| --- | --- |
| `playtest.js` | 通しの プレイテストを 動かし、落ちた 項目を まとめる。`--show`・`--old REF --files`・`--main`・`--rerun`・`--port` |
| `commit.sh "題" ["本文"]` | 決まりの 2行を つけて コミット（題・本文に モデルの 名前が あれば 止める） |
| `guard.js [比べる元]` | push の 前の 見張り（✖ は 直すまで push しない、⚠ は 目で 確かめる）。秘密は push する コミットごとに 見る |
| `push.sh` | 見張りを 通して 作業用の ブランチへ push（ネットの つまずきは やりなおす） |
| `skip-ci.js [比べる元]` | マージの 題に `[skip ci]` が いるか（make-promo.yml・ricepia-jp.yml の paths から 判定。読めない 書き方なら 安全がわで「いる」） |
| `merge.sh <PR>` | 「マージ」と 言われたら まず これ：pre-merge.sh → merge-plan.js |
| `pre-merge.sh` | マージの 前：main を 取りこむ → 見張り → プレイテスト → push → expectedHeadSha |
| `merge-plan.js <PR> [--allow-findings]` | マージの 支度を 確かめ（PR・先頭・Codex・[skip ci]）、merge_pull_request に わたす JSON を 出す |
| `post-merge.sh <SHA> <先頭SHA> [分]` | マージの あと：あとから 積んだ コミットが ないか 確かめる → ブランチを つなぎなおす → Vercel を 待つ |
| `run-wait.sh <ワークフロー> [控えた id]`・`--id <id>` | Actions の 実行が 終わるまで 待つ（引数1つなら いまの 実行の id を 出す。控えた id より あとの 最初の 実行に 相手を 決めて その id だけを 追う）。LINE リッチメニューの 差しかえで 使う |
| `selfplay.js 出力 [ゴール数]` | 地図の めいろを 遊ぶ 遊び手（つまずきの 記録・画面） |
| `env.js` | 共通の したく（Leaflet を `--ignore-scripts` で 取りだして キャッシュ、Chromium の 場所） |

プレイテストと 遊び手は、ネットに つながらなくても 動くよう Leaflet を キャッシュから 出し、Overpass には 問い合わせない（遠い 区域の 地図は 読めないので、5km 先の ゴールの 道すじは 出ない。これは テストの 場所だけの こと）。
